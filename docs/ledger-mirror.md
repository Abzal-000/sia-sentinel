# WORM-зеркало леджера: публичная append-only история доверия

**Статус: механизм готов и протестирован (2026-09-14); публикация зеркала
— решение оператора.** Этот документ объясняет, что уже сделано, что
остаётся человеку и почему это отдельное решение, а не технический шаг.

## Зачем зеркалу быть отдельным решением

Леджер TrustChain — суть продукта: тампер-эвидентная история квитанций.
С 2026-09-14 леджер живёт в двух местах: локально и в приватном репо
`Abzal-000/sia-sentinel` (вторая точка существования). Но приватный
remote — это резервная копия, а не доказательство: владелец репо может
переписать его историю силой (`git push --force`), и для внешнего мира
«история была такой» останется только слово владельца.

WORM-зеркало (Write Once Read Many) превращает git-remote в внешний
свидетель: отдельный публичный репозиторий, куда история леджера ТОЛЬКО
добавляется, никогда не переписывается, и любой человек может сверить
«историю в зеркале» с «историей в аттестациях» сам. Аналогия из
собственной архитектуры проекта: чекпойнты фиксируют голову, Rekor
фиксирует якорь, а зеркало фиксирует ВСЮ историю целиком и ежедневно.

Это и есть шаг от «приватная резервная копия» к «публичное доказательство
непрерывности»: каждый день, которого нет в зеркале, — день, который
нельзя впоследствии доказать не переписанным.

## Что уже сделано (не нужно повторять)

- `scripts/mirror_ledger.py` — публикация с тремя гейтами, каждый доказан
  красным в `tests/test_mirror_ledger.py` (6 тестов):
  1. **Локальная цепь VALID** до головы — зеркалить битую историю =
     реплицировать повреждение (отказ, exit 1).
  2. **Зеркало расширяет историю** — голова зеркала обязана быть строгим
     префиксом локальной; расхождение = человек-алерт «кто-то переписал
     одну из сторон», НЕ «автоконвергенция» (exit 2).
  3. **Только trust-bearing пути** в staging (ledger/checkpoints/anchors);
     черновики в зеркало не едут (exit 1).
- Выходные коды cron-friendly: 0 ок / 1 локальный отказ / 2 расхождение
  (человек!) / 3 нет remote.
- Гейт 2 живой проверен: текущая голова (seq=4) на remote — строгий
  префикс, «mirror already up to date».

## Что остаётся оператору (по порядку)

1. **Создать отдельный ПУБЛИЧНЫЙ репозиторий** (например
   `Abzal-000/sia-ledger-mirror`). Не ветку существующего приватного —
   именно отдельный публичный репозиторий: цель — внешний свидетель,
   а не ещё одна наша точка.

2. **Включить защиту ветки на хостинге** (GitHub → Settings → Branches →
   Add rule → master): «Restrict deletions» + запрет force-push. Это
   вторая половина WORM: скрипт не даст нам переписать историю локально
   (гейт 2), а хостинг не даст — на стороне push. Без правила на хосте
   append-only остаётся конвенцией, которую мы сами же нарушить можем.

3. **Прописать remote как `mirror`** (продуманное имя, не `origin`):
   ```bash
   git remote add mirror https://github.com/Abzal-000/sia-ledger-mirror.git
   ```
   И адаптировать один вызов в `scripts/mirror_ledger.py`: заменить
   `origin` на `mirror` в `mirror_head()`/`main()` (строки с
   `["fetch", ...]`, `["show", "origin/master:..."]`, `["push", ...]`).

4. **Запустить**: `python scripts/mirror_ledger.py` (см. гейты выше).
   Выход 0 — история опубликована; повторные запуски идемпотентны
   («already up to date»).

5. **Повесить на cron** рядом с `cron_ledger.sh` (позже, после деплоя):
   зеркало должно обновляться чаще, чем появляются записи: раз в час
   достаточно при текущем темпе.

## Честные границы (что зеркало НЕ доказывает)

- Зеркало фиксирует содержимое реестра на моменты пуши. Между пушами
  окно: запись, сделанная в 12:00 и зеркалированная в 13:00, час
  существовала только локально. Окно сужается частотой запуска.
- Зеркало на GitHub — доверие хостингу. Полная независимость — это
  публичный git-хостинг нейтральной стороны или S3 Object Lock (WORM
  bucket) как второй транспорт; с Gespalt-целью проекта — обычный
  компромисс этапа.
- Скрипт — guard против НАШИХ ошибок и лени, не против компрометации
  аккаунта GitHub (защита аккаунта — отдельная тема: 2FA, audit log).

## Почему «решение», а не «сделай сейчас»

Публикация леджера наружу — это публикация метаданных квитанций
(идентификаторы, хеши, суммы, таймстемпы) для всего мира. Для двух
записей, обе наших собственных, это безопасно (это уже публичные
аттестации — `artifacts/` в том же репо). Но решение о том, что «история
доверия SIA отныне публична в реальном времени» — это заявление о
позиции проекта (полная прозрачность), которое стоит сделать осознанно
и один раз, а не как побочный эффект технического шага.
