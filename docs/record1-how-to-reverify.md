# Запись №1: как посторонний перевыводит вердикт самостоятельно

*Назначение маяка — показать, что вердикт по паре моделей посторонний выводит
из опубликованной записи заново, независимо от того, окажется ли дешёвая
модель не хуже дорогой. Предсказательная вероятность вердикта «не хуже» по
пилоту — 27.6%, и это опубликовано вместе с обязательством.*

Запись №1: `gpt-oss-120b → gpt-oss-20b` (Groq), GSM8K, n=450, δ=5 п.п.
Вердикт: **non_inferior**, подтверждённая экономия **50.5%**.

Здесь нет шага «поверить». Каждое утверждение либо проверяется криптографией,
либо пересчитывается из первичных чисел. Всё выполняется на вашей машине;
единственные сетевые запросы — к публичному логу Rekor (Sigstore).

## Что понадобится

- Python 3.9+ и `pip install sia-verifier` — **версия 1.4.0+** (журнал
  чекпойнтов содержит несколько подписанных снимков и проверяется целиком;
  CLI видит лаг покрытия головы за последним чекпойнтом — advisory, а с
  `--require-coverage` — ворота; rederive сворачивает inclusion-proof
  Rekor локально. 1.3.0 на многоснимочном журнале честно падает —
  обновитесь, `pip install --upgrade sia-verifier`)
- Артефакты записи: `artifacts/record1/`, `flows/beacon.json`,
  `receipts/registry.jsonl`, `receipts/checkpoints.jsonl`
  (в репозитории SIA Sentinel; после публичного деплоя — скачиваются с сайта)

## Шаг 1. Подпись, цепь, чекпоинт — `sia-verifier`

```bash
sia-verifier artifacts/record1/attestation.json \
  --chain receipts/registry.jsonl \
  --checkpoint receipts/checkpoints.jsonl
```

(из корня репозитория; на Linux — `venv/bin/python`)

Проверяется: Ed25519-подпись квитанции ключом из `issuer.public_key`
(коммитмент пересчитывается поле-в-поле, включая манифест и `receipt_id`),
согласованность `claim.savings_verified` с подписанным `safety_approved`,
целостность хеш-цепочки леджера и подпись чекпоинта головы.
Ожидаемый вывод: `VERDICT: VALID`.

## Шаг 2. Перевывод вердикта — `sia-rederive`

Второй инструмент не принимает на слово вообще ничего — он пересчитывает
вывод из первичных чисел:

```bash
sia-rederive
# из корня репозитория (артефакты по умолчанию: artifacts/record1,
# flows/beacon.json, receipts/registry.jsonl); флаг --no-rekor — офлайн

Что именно сверяется (все девять проверок):

| # | Проверка | Откуда данные | Что доказывает |
|---|---|---|---|
| 1 | `dataset_sha256` | флоу (датасет лежит целиком в `flows/beacon.json`), аттестация, отчёт | все три документа говорят об одном датасете; хеш пересчитан из промптов |
| 2 | Якорь Rekor | `sha512` канона обязательства (с `anchor_reference=null`) против дайджеста живой записи `rekor:108e…41f00c8:2601942504` | обязательство с параметрами (δ, метрика, конфиги, цены) существовало ДО прогона — публичный свидетель вне инфраструктуры SIA |
| 3 | Парность b=10, c=4 | метки провалов отчёта: `failed_old(13)`, `failed_new(19)`, разность множеств | подписанная статистика соответствует сырым исходам |
| 4 | CI (MOVER), Макнемар | локальные формулы | опубликованный интервал и p-value не врут |
| 5 | Вердикт `non_inferior` | `ci_lower > −δ` И `mdd ≤ δ` | правило воспроизводится, ворота не переставлены |
| 6 | Экономия 50.5% | `total_cost_usd / calls` обеих сторон отчёта | отношение пересчитано из первичных чисел |
| 7 | Леджер | seq=1 (prereg) < seq=2 (квитанция), поля совпадают | обязательство предшествует результату |
| 8 | Привязка отчёта | `sha256(report) == receipt.code_hash` | числа, из которых перевыведен вердикт, сами пришиты к подписи |
| 9 | Inclusion-proof Rekor | RFC 6962-фолд (leaf из body записи, внутришардовый индекс, корень proof'а == корню подписанного checkpoint) — всё считается ЛОКАЛЬНО | ответ сервера Rekor не принимается на слово: запись действительно включена в подписанное дерево, а не «сервер так сказал» |

MDD считается по правилу пола из спеки §1.1: `p_disc = max(10% допущение,
наблюдённая дискордантность 3.1%)` — опубликованный MDD 4.18 п.п.
консервативен относительно наблюдённого, а не наоборот.

Ожидаемый вывод: `REDERIVED:    YES`.

## Шаг 3. Совсем без доверия к коду SIA (по желанию)

`rederive` вызывает репозиторный `build_preregistration_commitment` для
канона обязательства. Полностью независимый путь: собрать обязательство
руками из `flows/beacon.json` по полям спеки §1.2
(`docs/attestation-spec.md`), занулить `anchor_reference`, сериализовать
`sort_keys=True, separators=(',',':')`, взять `sha512` — должно совпасть с
дайджестом записи Rekor (`af720aad…7c33a8b6`). Формулы шагов 3–5 описаны
в §1.1 спеки словами, воспроизводятся на любом языке за ~50 строк.

## Что проверяется живым запросом

Один запрос: `GET https://rekor.sigstore.dev/api/v1/log/entries/<uuid>`
(плюс при желании inclusion-proof против подписанного дерева Sigstore —
эндпоинт `/api/v1/log/entries/{uuid}/proof`). Никаких ключей SIA не нужно.
Флаг `--no-rekor` пропускает этот шаг целиком: он не «проверяет якорь
офлайн», он его ПРОПУСКАЕТ (помечает `anchor_rekor.skipped_reason`).
Полный автономный путь без сети — сверка с `.cache/record1_payload.bin`
operator'ом-локально; для внешнего проверяющего его нет, и сила якоря
именно в том, что запись живёт в чужом логе (Rekor), поэтому красное
слово «проверено» без живого запроса не произносится.

## Шаг 4 (опционально). Свежий повтор — `sia-replay` (Б2)

Перевывод (шаг 2) проверяет, что ЗАПИСЬ непротиворечива. Сильнейший шаг:
прогнать тот же датасит самостоятельно против тех же эндпоинтов и
сравнить с записью. Допуск при этом — задекларированный в обязательстве
`replay_tolerance 5%`, правило `directional-one-sided:toward-claim`:
счёт расхождений односторонний, «в пользу заявления»:

```bash
# Повторите прогон сами (свой Groq-ключ, ~126K токенов, $0 на free-тарифе):
./venv/Scripts/python.exe audit_cli.py --flow flows/beacon.json --out my_replay.json

# Сравните ваш повтор с опубликованной записью:
sia-replay --flow flows/beacon.json --record artifacts/record1/report.json --replay my_replay.json
```

Ожидаемый вывод честного повтора: `VERDICT: WITHIN TOLERANCE` (наблюдаемый
поэлементный дрейф бесплатного пула — единицы процентов, симметричный).
Что означает `REPLAY MISMATCH`: расхождений «к заявлению» больше допуска —
либо повторитель столкнулся с реальной деградацией качества новой модели,
либо ему стоит ещё раз проверить воспроизводимость у себя (злой умысел
протокол отделит от дрейфа только статистически, не олимбийски).

## Честные границы (то, что НЕ проверяется)

- **Кто отвечал:** отпечатки обслуженных бэкендов (`served_model_names`,
  coverage) публикуются в манифесте, но верифицируются провайдером, не нами.
- **Повторный прогон:** `replay_tolerance 5%` (односторонний к заявлению)
  задекларирован в обязательстве; инструментарий сравнения чужого повтора
  с записью (Б2) — в разработке, его отсутствие раскрыто в `declared_limits`.
- **Цены:** зафиксированные в записи тарифы Groq от 2026-08-26; сверка
  с текущими ценами — отдельный вопрос экономии «сегодня».
