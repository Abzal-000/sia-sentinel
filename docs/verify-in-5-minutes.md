# Как проверить квитанцию экономии ИИ за 5 минут

*Стандарт `sia-attestation/1` · независимая верификация без доверия к аудитору*

Любая компания может заявить: «мы сократили расходы на ИИ на 60%». Квитанция
Proof-of-Savings — это криптографическое доказательство такого заявления.
Ключевое слово — **доказательство**: вам не нужно верить аудитору на слово.
Вот как проверить любую аттестацию SIA самостоятельно, за пять минут.

## Что вам понадобится

1. **Документ аттестации** — JSON, который отдаёт `GET /v1/attestations/{id}`
   (публичный, без авторизации). Сохраните его как `attestation.json`.
2. **Пакет `sia-verifier`** — референсный независимый верификатор:

```bash
pip install sia-verifier
```

Единственная зависимость — `cryptography`. Никаких сетевых вызовов.
Пакет ставит четыре команды: `sia-verifier` (подпись/цепь/чекпоинт),
`sia-rederive` (перевывод вердикта записи из опубликованных артефактов —
см. [`record1-how-to-reverify.md`](record1-how-to-reverify.md)),
`sia-replay` (сравнение независимого повторного прогона с записью —
исполняет задекларированный `replay_tolerance`; см. раздел 4 там же) и
`sia-holdout` (инструмент аудитора holdout, `docs/holdout-design.md`).

## Шаг 1. Запустите верификатор

```bash
sia-verifier attestation.json
```

Вы увидите вердикт:

```
spec:                 sia-attestation/1
attestation_id:       77f49f07c00f4f52b9810db7bedb308e
receipt signature:    VALID
claim consistent:     yes
VERDICT: VALID
```

Код выхода `0` — аттестация валидна (можно встраивать в CI), `1` — невалидна.

## Шаг 2. Что именно проверено

- **Подпись квитанции (Ed25519).** Квитанция внутри аттестации подписана
  приватным ключом аудитора. Верификатор восстанавливает канонический
  коммитмент из полей квитанции — включая `receipt_id` и манифест
  воспроизводимости — и проверяет подпись публичным ключом из поля
  `issuer.public_key`. Любое изменение хотя бы одного бита ломает подпись.
- **Согласованность заявления.** Публичное поле `claim.savings_verified`
  обязано совпадать с подписанным `receipt.safety_approved`. Подделать
  «экономия подтверждена» без приватного ключа невозможно.
- **Формат стандарта.** Поле `spec` должно быть `sia-attestation/1`.

## Шаг 3 (усиление). Проверьте хеш-цепочку

Каждая квитанция включена в append-only журнал TrustChain. Если у вас есть
выгрузка журнала (`registry.jsonl`), проверьте, что запись не удалена, не
вставлена и не подменена:

```bash
sia-verifier attestation.json --chain registry.jsonl
```

Верификатор пересчитает хеш каждой записи и подтвердит, что аттестация
присутствует в цепочке.

## Шаг 4 (усиление). Проверьте чекпоинт

Голова цепочки периодически якорится подписанным чекпоинтом — коммитментом на
`(seq, head_hash, tree_size, root_hash)`. Если чекпоинт опубликован во внешнем
источнике, он фиксирует состояние журнала на момент времени:

```bash
sia-verifier attestation.json --checkpoint checkpoint.json
```

## Шаг 5 (усиление). Проверьте включение в Merkle tree head

Самая сильная проверка без выгрузки журнала: докажите, что конкретная запись
входит в подписанный tree head. Аудит-путь сворачивается **локально** —
серверу нельзя верить на слово даже в этом:

```python
from sia_sentinel import SentinelClient

client = SentinelClient("https://sentinel.yourdomain.com")
verdict = client.verify_inclusion("77f49f07c00f4f52b9810db7bedb308e")
assert verdict["included"]  # leaf сворачивается в root_hash tree head
```

Три строки, и запись доказуемо находится в текущем состоянии журнала. SDK
скачивает доказательство и tree head и сворачивает RFC 6962 audit path
локально (stdlib, без доверия к ответу сервера). На стороне независимого
верификатора то же самое выглядит так:

```python
import httpx
from sia_verifier import verify_inclusion

proof = httpx.get("https://sentinel.yourdomain.com/v1/ledger/inclusion/77f49f07...").json()
head = httpx.get("https://sentinel.yourdomain.com/v1/ledger/head").json()

assert verify_inclusion(
    proof["entry_hash"], proof["leaf_index"],
    head["tree_size"], head["root_hash"], proof["proof"],
)
```

Если у вас есть два состояния журнала (например, внешний анкор и текущая
голова), `GET /v1/ledger/consistency?from=&to=` + `verify_consistency`
докажут, что история только дополнялась, но не переписывалась.

## Что верификатор НЕ проверяет (честно)

- Поля `verification.*` в документе — это живое мнение сервера аудитора; они
  **не** входят в подписанный коммитмент и намеренно игнорируются.
- Публичный ключ берётся из самого документа. Для максимальной гарантии
  сверьте `issuer.public_key` с ключом, опубликованным аудитором по
  независимому каналу (сайт, реестр ключей).
- Криптография подтверждает целостность и авторство, но не методологию
  аудита. Методология зафиксирована в манифесте воспроизводимости внутри
  квитанции: датасет, конфигурации, цены, сиды — всё, что нужно, чтобы
  повторить прогон.

## Программная проверка

```python
import json
from sia_verifier import verify_attestation

attestation = json.load(open("attestation.json"))
verdict = verify_attestation(attestation)

assert verdict.valid, verdict.reasons
```

## Итого

| Проверка | Команда | Что доказывает |
|---|---|---|
| Подпись + заявление | `sia-verifier attestation.json` | Квитанция подлинная, заявление не подделано |
| + цепочка | `... --chain registry.jsonl` | Запись не удалена/подменена в журнале |
| + чекпоинт | `... --checkpoint checkpoint.json` | Состояние журнала зафиксировано на дату |
| + включение | `client.verify_inclusion(id)` | Запись входит в подписанный Merkle tree head |
| + согласованность | `verify_consistency(from, to)` | История дополнялась, но не переписывалась |

Полная спецификация формата: [`attestation-spec.md`](attestation-spec.md).
Исходный код верификатора: [`verifier/`](../verifier/) в репозитории SIA Sentinel.
